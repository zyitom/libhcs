# 控制环里的时间：需要什么、不需要什么

> **文档类型**：背景说明（设计取舍与判据）
> **适用范围**：`firmware/hpm_board/` 提供的时间能力，以及使用它的上位机控制环（`~/Desktop/HCS`）
> **状态**：现行有效
> **相关文档**：[SOF_TIMEBASE.md](SOF_TIMEBASE.md)（时间轴本身的实现与实测） · [AGENTS.md](AGENTS.md)（板级规范） · [../../HOST_TUNING.md](../../HOST_TUNING.md)

## 摘要

这份文档回答的是"**控制环到底需要哪些时间信息**"，以及一个反复被问错方向的问题——
不是"时钟要多准"，而是"**每个测量有多老、每条命令什么时候真的生效**"。
结论先行：**控制环不需要 PC 的 Unix 时间戳，也几乎不需要跨板同步；它需要的是数据年龄，
用来把死区外推补偿掉。** 什么时候才真的需要共享时间轴，见第 4 节的判据表。

## 1. 时间戳的用途是外推，不是对时

控制律里唯一真正吃时间的量是 `dt`，而 `dt` 的**尺度误差等于增益误差**——差 1 ppm 等于
Kd 差 1 ppm，毫无意义。所以"时钟准不准"对 PID 几乎无关。

真正伤人的是三件，没有一件是时钟准度问题：

1. **采样时刻抖动**：微分是 `Δθ/Δt`，用标称 dt 去除一个实际在抖的间隔，等于放大噪声；
2. **测量到执行的延迟**：决定相位裕度；
3. **漏掉的迭代**：按次数推进的参考轨迹会被悄悄拉长。

时间戳解决的是第 1、2 条，方式是**外推到执行时刻**：

```
θ_送进控制器 = θ_测量 + ω × (t_执行 − t_测量)
```

死区 2~3 ms、角速度 200 deg/s 时，这一步直接补掉 0.4~0.6 度的相位滞后。
**这就是时间戳在控制里的全部价值**——知道"这个数多老"，然后把它补回去。`[推断，基于死区预算]`

## 2. 死区预算：决定闭环带宽的那个数

以"一发一收"的 CAN 电机（命令触发反馈）为例，各环节量级：

| 环节 | 典型 | 抖动 | 来源 |
|---|---|---|---|
| 上位机循环周期 1 kHz | 1000 us | 调度抖动，未调优主机可达几十 us | `[结构]` |
| USB 下行 + 板转发 + 上行 | 约 100 us | 约 +-30 us | `[实测]` 板级 RTT p50 99.8 / p99 125 |
| CAN 命令帧上线（经典 1 Mbit，8 字节含填充 111~135 bit） | 约 130 us | 仲裁等待 | `[计算]` |
| 电机内部处理 + 回复帧 | 电调决定 + 约 130 us | — | `[计算]` |

合计**约 2~3 ms**。经验法则：无预测的 PID 闭环带宽 <= 1/(10 x 死区) `[经验法则]`，
即 **50 Hz 上下**。

**在这个预算面前，USB 占 3~5%，纳秒级同步在小数点后看不见。** 想提升闭环质量，能动的只有
两件事：**把死区变小**，或者**把死区变成常数然后补偿它**。后者往往更划算——
**抖动的延迟比大的延迟更难对付**。

### 2.1 CAN 总线才是先撞到的墙

一发一收 = 每电机每周期约 **260 us**（经典 CAN 1 Mbit）。拿它乘以同总线电机数，
对比控制周期：

- 4 个电机一条线：4 x 260 = **1040 us > 1 ms**，1 kHz 已经跑满；
- CAN-FD 1M/5M 可压到约 120 us/电机，同样 4 个能到 2~3 kHz——**但前提是电机支持 FD**。

电机不支持 FD 时，剩下的杠杆只有：**分总线**（本板 2 路 / 6E8Y 4 路）、
**减少每周期帧数**（协议允许的话一帧带多个电机）、**分层降频**。

## 3. 为什么到处都在拟合，成本多少

| 拟合 | 跑在哪 | 频率 | 规模 |
|---|---|---|---|
| 微帧 -> 机器定时器（`sync/timebase.cpp`） | 板子主循环 | 20 ms | 128 点 |
| 微帧 -> GPTMR（`sync/pulse.cpp`） | 板子主循环 | 64 ms | 128 点 |
| 微帧 -> 主机 steady_clock（`libhcs/time/timeline.cpp`） | 主机 | **250 ms**（跟 keepalive） | 256 点 |

**主机侧一秒 4 次最小二乘，几微秒**；x86 上真正的开销是 1 kHz 的 executor 和 libusb
事件线程。拟合不是算力问题。

非拟合不可的原因有两个，都是物理的：

1. **两个独立晶振**：板子 24 MHz 与主机 USB 时钟差约 +80 ppm `[实测]`。按标称常数换算，
   50 ms 提前量就错 4 us。
2. **单次采样带中断抖动**：一次 SOF 中断进入抖动 +-0.5~2 us；128 点平均后残差 17~24 ns
   `[实测]`。**纳秒级精度整个来自这一步平均。**

**替代方案是硬件**：`USB0_SOF -> TRGM -> PTPC 捕获` 在硅片里锁存，没有软件路径，也就没有
抖动可平均（SOF_TIMEBASE.md 4.7）。拟合是没走那条路时的软件替代品。

## 4. 什么时候需要共享时间轴

| 场景 | 需要吗 | 理由 |
|---|---|---|
| 单板 + 一发一收电机 | **不需要** | 反馈由命令触发，数据年龄确定；同板多帧一个 USB 包背靠背进队列 |
| 多板但各控各的 | **不需要** | 各自闭环独立，早晚几十 us 没有物理意义 |
| 多板必须同一时刻施力 | 需要，但只要"执行时刻"这一件 | 不需要 Unix，不需要 ns |
| 多个传感器要落在同一条轴上做状态估计 | 需要 | 例如 IMU 在 A 板、编码器在 B 板 |
| 任何情况 | **都不需要 PC 的 Unix 时间** | 命令说的是整数微帧号，不经过任何时钟换算 |

第三种也要先问物理意义：机械带宽几十 Hz 的系统，跨板错开 30~100 us 是一个周期的 0.3%，
**大概率淹没在电机自身响应里**。**先量，再决定值不值得做。**

> **PC 时钟误差不可能产生跨板 skew**：所有板收到的是同一个整数 k，主机估计错了只会把整个
> 动作平移同一个量。见 SOF_TIMEBASE.md 4.2。

## 5. IMU 是独立串口设备时的架构

成品 IMU（自带晶振、串口、1 kHz 自由流）与板载 BMI088 的差别，直接影响闭环怎么搭：

| | 板载 BMI088 | 成品 AHRS（串口） |
|---|---|---|
| 融合在哪 | 主机（Mahony，参数可调） | 传感器内部，不可见 |
| 采样时刻谁定 | 板子（主动读 SPI，可打时间戳） | 它自己的晶振，只知道包何时到 |
| 丢一个样本 | **累积误差**（陀螺是增量） | **无后果**（姿态是绝对量） |
| 群延迟 | 自己控制 | 厂家决定，常见几 ms，**不透明** |

因此的做法：

1. **接板子的串口，不要接 PC 的 USB 转串口**——转接器的 latency timer 默认能到 16 ms，
   且到达时刻受 PC 调度支配。板端有 UART 空闲线中断（`rxidle_config`），知道一帧何时收完。
2. **先去查它的内部滤波带宽**：几 ms 的群延迟比整条 USB 往返（100 us）大两个数量级，
   多半是它在吃你的相位裕度。`[需查厂商手册]`
3. **拍频要处理**：它的 1 kHz 与控制栅格是两个晶振，会周期性出现一拍 0 个 / 2 个包。
   绝对姿态 + 外推能自然吸收；更干净的做法是让 IMU 包到达驱动控制拍。

## 6. 已知缺口

### 6.1 板端：UART 数据没有时间戳

| 数据 | 时间戳 |
|---|---|
| CAN 帧 | 有，`timestamp_us`（硬件 TSU） |
| GPIO | 有，`timestamp_quarter_us` |
| **UART** | **没有**（`UartDataView` 只有 `uart_data` / `idle_delimited`） |

板子已经有空闲线分帧，**只差在 idle 中断里读一次机器定时器并随包上送**。
这是"串口 IMU 闭环"的前置条件，没有它就无法外推。

### 6.2 板端：同一块板上有两个时基

CAN 时间戳走 **PTPC**（挂 PLL0，分数分频 + 展频，几百 ppm 游走），IMU/GPIO 走
**机器定时器**（晶振 / 6，1.8 ppm）。**两者直接相减是错的**——SOF_TIMEBASE.md 5.4 节
五次失败都栽在这里。换算用现成的 `timebase::microframe_q16_at_ptpc()`。

### 6.3 上位机：PID 没有 dt，跳拍静默

- `hcs_core/.../pid/pid_calculator.hpp`：积分直接累加、微分裸差分，**dt 折进 Ki/Kd**，
  默认每拍等长；
- `hcs_executor/src/executor.hpp` 超时会**整拍跳过**并计数 `skipped_count`，
  **但控制器不消费它**——跳一拍就是积分少加一份、微分把两拍当一拍，无人知晓；
- 一发一收的电机上还多一层：命令没发 = 反馈也没回，那几毫秒连测量都没有。

**先去翻 executor 日志看 `skipped_count` 是不是常年 0**；是 0 就不用管。`[未实测]`

### 6.4 上位机：`hipnuc.hpp` 是死代码，且有越界

`hcs_core/src/hardware/device/hipnuc.hpp` 已入库（commit `c044a793`），但
**当前没有任何文件 include 它**——原来接在 `hero.cpp` 上，那个文件在
`5c7f3fb3`（迁移 libhcs v3）里被删了。

另外它只解 `0xD1`（四元数）一个标签，`length` 硬编码 17：**模块一旦配置成输出多项，
CRC 就会失配**。而且内联 `stream.read()` 的边界判断写反了
（`if (size < data_length) size = data_length;`），会拷贝超过调用方缓冲区的字节——
**接上去之前必须先改成取二者较小**。`[读代码得出，未实测]`
