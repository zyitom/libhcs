## 1. 最终结论

### 1.1 瓶颈是"每秒多少次传输"，不是"每秒多少字节"

单板 USB 传输率的天花板 `[实测]`：

| 配置 | URB/s（8 字节 payload） |
|---|---|
| 单端点对 | **64012 / 64008 / 64012**（离散度 0.006%） |
| 双端点对（分 CAN） | 50792 / 50377 / 50868 |

64000 恰好等于 `8000 微帧/秒 x 8`，即主机每微帧给这个设备 8 个 bulk 事务。
**per-device**：双板 CAN-free 实测 128880，完美线性，控制器远未饱和。

### 1.2 但把包做大，吞吐几乎线性上升

同一固件（分端点开启），只改每个 URB 的 payload 大小 `[实测]`：

| payload | URB/s | **MB/s** | 线上包数 |
|---|---|---|---|
| 8 B | 50821 | 0.41 | 1 |
| 64 B | 48008 | 3.07 | 1 |
| 256 B | 42619 | 10.91 | 1 |
| **448 B** | 35668 | **15.98（最优）** | 1 |
| 511 B | 16571 | 8.47 | **2** |
| 512 B | 16168 | 8.28 | 2 |
| 1023 B | 14498 | 14.83 | 3 |

**payload 从 8 涨到 256 字节（32 倍），URB 率只掉 16%**，有效吞吐涨 26 倍。

### 1.3 拐点可以从代码算出来，精确到 1 个字节

每条 UART 记录的固定开销**由代码唯一确定**：

| 部分 | 字节 | 依据 |
|---|---|---|
| `FieldHeader` | 1 | `kUart0 = 11`，而 `use_extended_field_header` 的判据是 `> 0xF` |
| `UartHeaderExtended` | 2 | payload >= 4 即走扩展长度（`Bitfield<2>`） |
| **合计** | **3** | |

USB 最大包 512 字节，所以 **payload <= 509 时线上恰好一个包**。实测逐字节确认：

| payload | 线上 | URB/s | 数据包数 |
|---|---|---|---|
| 508 | 511 | 32465 | 1 |
| **509** | **512** | **32462** | **1** |
| **510** | **513** | **21092** | **2** |
| 512 | 515 | 16447 | 2 |

**拐点精确落在 509 / 510 之间，与代码算出的 `512 - 3 = 509` 完全一致。** `[实测]`

> **一个被推翻的机制猜测**：我最初以为 512 会因为 `LIBUSB_TRANSFER_ADD_ZERO_PACKET`
> 追加 ZLP 而腰斩。**不对**——payload 509（线上正好 512）仍在高位。ZLP 只是一个约
> 0.35 us 的空事务，被每 URB 约 20 us 的固定开销淹没了。**真正贵的是第二个满数据包。**

### 1.4 每多一个数据包，多付约 30 us 调度开销

把 URB 间隔扣掉线上传输时间，剩下的就是主机的固定调度开销：

| 每 URB 数据包数 | URB 间隔 | 扣掉线上时间 |
|---|---|---|
| 1 | 19.7~30.8 us | **约 20 us** |
| 2 | 60.8 us | 约 52 us |
| 3 | 69.0 us | 约 51 us |

**多一个满包比多发一个 URB 还贵**，所以做大传输是反效果：

```
payload  509（1 个包） -> 32462 URB/s -> 16.52 MB/s   最优点
payload 1023（3 个包） -> 14498 URB/s -> 14.83 MB/s   更差
```

> **这 20~30us 是吞吐量的倒数，不是延迟预算里的一项。** 它由"饱和洪泛下的 URB 间隔
> 减去线上时间"算得（1/32462 URB/s），衡量的是每个 URB 占用多少条串行化的主机产能。
> 单次传输的**延迟**里，Linux 自己的代码只有 5~8us（kprobe 四段分解，
> `HOST_TUNING.md` 11.9.1）。**两者相差一个数量级，来自完全不同的工况；
> 把本节的数字当延迟项相加，会得出"主机占大头"的错误结论。**
> 已有人这样算错过一次，见 `HOST_TUNING.md` 11.11.6。`[实测 2026-09-05]`

**16.5 MB/s 是这条链路的实际天花板**（HS 理论约 53 MB/s，达到 31%）。
`kProtocolBufferSize = 1023` 满载时是 3 个包——能用，但不是最优；真要提吞吐，
应当让单次传输的线上长度停在 512 以内。

### 1.5 所以极限在哪

| | 能力 | 本项目需要 | 余量 |
|---|---|---|---|
| USB 字节吞吐 | **16.52 MB/s** `[实测]` | 双路 CAN-FD 满载约 435 KB/s | **约 37 倍** |
| USB 传输率 | 35k~50k URB/s | 1 kHz 控制环 = 1000 URB/s | **约 40 倍** |
| CAN 线速 | 19.8k f/s x 2 | —— | **已到顶** |

**CAN 线速才是这条链路的真实约束，USB 差着两个数量级。**

| # | 改动 | 位置 | 实测效果 |
|---|---|---|---|
| 1 | TinyUSB 0.21 迁移 + 3 个上游修复 | 共享 submodule，已 push | SETUP 撕裂**正确性**修复；dcache + ctz 合计 +1.24% 包率 |

| 3 | ~~CAN 独立端点对（`SPLIT_CAN_ENDPOINT`）~~ | 描述符 + 协议 + host SDK | ~~UART 线速下 p99 143.9 -> 122.8 us~~ **已作废，见 4.5** |

## 3. 被实测否掉的七个方向

| 方向 | 结果 | 判据 |
|---|---|---|
| **multi-qTD** | **零收益** | 用 15 行的 copy-then-arm 做等效实验：turnaround 2.22 -> 1.27 us，**包率 63999/63996/64002 vs 63988/63988/63991，完全一致** |
| 热路径进 ILM | **净倒退** | 包率 +0.11%，主循环周期 **−4.0%**（跨 2 GB 段调用，`jal` 退化成 `auipc+jalr`） |
| 加更多端点 | **−21%** | 第二对端点的空闲 IN 侧持续 NAK，占掉调度槽 |
| `CFG_TUD_TASK_EVENTS_PER_RUN` | **惰性** | 主循环 0.72us 一圈，队列几乎永远 <= 1 个事件 |
| host transfer 池加深 | **无关** | 32 / 64 / 128 / 256 全部约 50.5k |
| xHCI IMOD 寄存器 | **非瓶颈** | 40us 中断间隔 vs 池里 1 ms 的活，饿不着控制器 |
| `RX_NEED_ZLP` 多包接收 | **不适用** | bulk OUT 遇短包即结束，我们每个包都是短包 |

### 3.1 关于 multi-qTD 的额外说明

上游 master 至今是 `qtd[TUP_DCD_ENDPOINT_MAX][2]`，注释写明
**"for portability, TinyUSB only queue 1 TD for each Qhd"**——是刻意选择，不是遗漏。
搜遍 PR / issue / changelog，**无人做过**。

而它唯一能改善的设备侧 turnaround 已被证明不在关键路径上：设备每 17 us 就能交出一个包，
主机每 15.6 us 才要一个，**设备已经比主机快 12 倍**。

## 4. 我写错又更正的五处结论

**这一节比前面都重要。** 四次都是同一类错误：**用不充分的数据下了过强的结论**。

### 4.1 "注入延迟"线性模型 —— 混杂实验，作废

用忙等人为拉长 turnaround，得出 `cycle = 1.2~1.4 x turnaround + 13.5 us`，据此推出
multi-qTD 值 +23~35%。

**错在忙等同时改变了两个变量**：未 arm 窗口 **和** 每包 CPU 总量。后来只搬动工作位置
（CPU 总量不变）时 cycle 纹丝不动，证明起作用的不是前者。

> **教训：一次只改一个变量。**

### 4.2 "双板 104k 说明主机争用 13%" —— 错，那是 CAN 线速

CAN-free 双板实测 **128880**，干净的 2 倍。此前的 104433 是被 CAN 线速限住的。

### 4.3 "分端点纯赚 p99" —— 错，它是个交叉点

> **状态：历史记录。** 这一节纠正的是「纯赚」，但它得到的「交叉点」结论本身在
> 2026-09-05 又被推翻——见 4.5，现在分端点在任何负载下都不赢。本节的教训
> （对照组也要跑够轮数）仍然成立。

对照组只跑了三次（105.0 / 117.3 / 117.5），我把那个 105 当成了噪声。
8 轮复测：`SPLIT=1` 稳定在 117.6~118.2，`SPLIT=0` 稳定在 105.1~111.0。**是真差异。**

| UART 负载 | `SPLIT=0` p99 | `SPLIT=1` p99 |
|---|---|---|
| 0 | **~107** | 118.0 |
| 10 kB/s | 120.3 | 120.0 ← 交叉点 |
| 25 kB/s | 138.4 | **122.0** |
| 92 kB/s | 143.9 | **122.8** |

> **教训：对照组也要跑够轮数。**

### 4.4 "Linux 没有旋钮能改" —— 太武断

xHCI 有 **IMOD 中断节制寄存器**（本机 `0xa0` = 40 us），有文档、有内核补丁、
可通过设备树属性 `imod-interval-ns` 配置——**但那只对 ARM/SoC 的 platform xHCI 有效，
x86 的 PCI xHCI 没有设备树，没有暴露路径**。

结论没变（它本来也不是瓶颈），但"没有旋钮"这个说法是错的。

> **教训：先查机器，再下结论。**

### 4.5 「分端点在高 UART 负载下赢」—— 2026-09-05 复现失败，已默认关闭

4.3 修正后留下的结论是「约 10 kB/s 以上分端点赢」。**同一个 rig、同一个 `uartcontend`、
交替复测，这个交叉点不存在**：

| UART 负载 | 不分端点 p50 / p99 | 分端点 p50 / p99 |
|---|---|---|
| 0 | **98.9 / 107~108** | 105.2 / 127 |
| 82 kB/s | **100.8 / 137.0~137.6** | 118.3~118.7 / 143.0~144.3 |
| 92 kB/s | **103.5 / 146.8** | 118.6 / 145.6~146.6 |

包率同时是 63.4k vs 49.2k。绑核与不绑核两种主机状态下排序一致，所以**不是主机调度抖动
被绑核消掉了**。

**2026-08-07 测出相反结果的原因是负载轴对不上。** 本节以前所有测量用的都是
`uartcontend ... 2 4 6 8`，而**本机只有 CPU 0~7**，`8` 让 `sched_setaffinity` 返回
EINVAL、负载线程保持游离。复刻实测：`load_core=8` 时 `offered=30.1 kB/s (asked 92)`，
两条曲线与空载对照逐位重合；`load_core=5` 时 `offered=119.8 kB/s`，超过 921600 的线速。
**旧表里标着 92 kB/s 的那一行实际不是 92。** 使用纪律：先看 `offered=` 再看分位数。

分端点的机制本身没错——它把 p99 的负载敏感度从 +39 us 削到 +20 us，"削掉约一半"成立。
**但它的起点高 22 us，而这是个恒定截距**（第二对 IN 端点只要存在就被轮询，与有无数据
无关，见上）。**截距赢不了斜率**，所以交叉点不存在。`[实测]`

**另外两项此前写错的细节：**

1. **代价与 URB 数量无关，是二值的。** 之前归因于「IN 侧挂着 16 个 URB」。实测 0 个 =
   63.1k，1 / 2 / 4 / 8 / 16 个全是 49.2k——控制器只要环非空就持续轮询。**没有把池调浅
   的折中方案。**
2. **只分下行是免费的，但也没有用。** OUT 端点不被空轮询，且板端无条件读管道 1 的 OUT，
   所以这个模式零固件改动、零包率代价；实测延迟与不分端点无法区分（100.8 / 137.5）。
   **下行侧本来就没有可削的 head-of-line 代价。**

交付默认因此改为 `AdvancedOptions::enable_priority_can_channel = false`。

## 5. 最重要的一个测量教训：整轮都测错了工况

**本轮几乎所有延迟数字都是 `gap=0` 的紧凑 ping-pong 测的，而真实控制环是 1 kHz。
两者的结论方向相反。** `[实测 2026-08-07]`

| 工况 | p50 | p90 | p99 | p99.9 | **jitter (p99−p50)** |
|---|---|---|---|---|---|
| `gap=0`（本轮一直在测） | 99.8 | 101.4 | 118.4 | 123.3 | **18.6 us** |
| **`gap=1000`（真实 1 kHz）** | **121.9** | 123.7 | 129.3 | 139.4 | **7.4 us** |

**真实工况下 p50 差 22 us，但 jitter 好 2.5 倍。** 拿 `gap=0` 的 p50 99.8 去承诺产品指标
是错的——1 kHz 控制环实际会看到约 **122 us**。

### 5.1 那 22 us 不是 C-state

用 `host-tuning.sh --pmqos` 锁死 C-state 复测：

| gap=1000 | p50 | p99 | p99.9 |
|---|---|---|---|
| 默认 | 121.9 | 128.5 | **139.0** |
| **+ `--pmqos`** | 122.1 | 126.8 | **129.9** |

**p99.9 改善 9 us，p50 完全不动。** 所以 22 us 是别的东西——最可能是"冷管道"：
`gap=0` 时主机始终有 64 个 URB 在飞，控制器一直在服务这个端点；`gap=1000` 时管道空了，
那唯一一个 URB 要等下一个服务槽（约 15.6 us）。**请求-响应模式的结构性代价，板端改不了。**
`[推断]`

> **2026-09-05 更正：这条 `[推断]` 的归因是错的，代价本身仍在。** 双 HS 板 rig 上
> gap=0 p50 98.9-99.0 vs gap=1000 p50 107.9-108.8，约 9us 的代价复现。但两条针对
> "冷管道"的干预都失败了：**给管道灌背景流量反而 +9us**（10.6 / 42.3 / 96.5 kB/s
> 三档一样高，是恒定截距而非斜率，即排队代价不是预热）；**把 `sleep_for` 换成同占空比
> 的忙等反而 +16us**（3/3 轮，一轮 max 冲到 1088us）。所以那 9us 既不是管道冷、
> 也不是应用线程冷，**目前无解释**。详见 `HOST_TUNING.md` 11.11.4。`[实测 2026-09-05]`

### 5.2 可操作的结论

**1 kHz 控制环若在意 p99.9，测量和运行时都应当挂着 `--pmqos`**（值 9 us）。
`host-tuning.sh` 里原来写"只值约 2 us 的 p99"——那是 `gap=0` 测的，对控制环低估了，
已在脚本注释里更正。

## 6. 测量方法的坑

### 5.1 别用带 CAN 的模式测 USB 上限

`usb_packet_rate split3` 每次迭代发两条 CAN，**被 19.8k f/s 的 CAN 线速限住**，
测到的 57.6k 不是 USB 上限。新增的 `uartonly` 模式（不含任何 CAN）才测得到端点本身。

### 5.2 用小包测出来的"包率"会误导

8 字节 payload 测出 50821 URB/s，看着像天花板，实际只是 0.41 MB/s ——
**16 MB/s 能力的 2.5%**。要测吞吐必须扫 payload 大小。

### 5.3 遥测的仪表盲点

`can_diag` 的 USB 时间戳只埋在 `tud_vendor_rx_cb` 的 itf-0 分支。分端点开启时 CAN 走
itf-1，遥测只反映承载 UART 的那条管道（实测报 18k 而主机报 57k）。
**测饱和必须先把 split 关掉。**

### 5.4 `dual_board_test` 的 stdout 是全缓冲的

重定向后被 timeout 杀掉会丢掉全部结果，看起来像"什么都没跑"，实际早就跑完了。
**用 `stdbuf -oL`。**

### 5.5 libusb 的 close 不会可靠取消第二个接口上的 IN 传输

实测 32 个 RX transfer 里有 6~16 个在 `libusb_close()` 之后仍未完成，
`handle_events()` 于是死等一个到不了 0 的计数——表现为**测量跑完了、进程不退出**。
正确顺序是 **cancel -> 等收割 -> 再 close**，并给事件循环加有界超时兜底。

## 7. UART 自身的延迟与丢包 [实测 2026-08-07]

**结论先行：UART 延迟的 93% 是 921600 波特率的线上时间，USB + 板端只占 50~96 us。
零丢失、零错序。要降 UART 延迟只能提波特率，和 USB 无关。**

此前各轮只把 UART 当作 CAN 测量的干扰源，从没测过它自己。新增
`dual_board_test uartlatency [samples] [bytes] [ca] [cb] [cmain]` 补这个缺口。

| chunk | 线上时间（10 bit/字节） | p50 总延迟 | **减去线上** | jitter (p99−p50) |
|---|---|---|---|---|
| 8 B | 86.8 | 147.8 | **61.0** | 27.8 |
| 32 B | 347.2 | 396.7 | **49.5** | 29.6 |
| 64 B | 694.4 | 745.9 | **51.5** | 33.2 |
| 128 B | 1388.9 | 1471.3 | 82.4 | 27.7 |
| 256 B | 2777.8 | 2873.6 | 95.8 | 26.9 |

每档 2000 样本，**timeout 0，mismatch 0**。

**丢包**：`dual_board_test uart 20000` = **1,280,000 / 1,280,000 字节，mismatches=0**。
`uartcontend` 在线速下报 offered 95.0 / delivered 94.0 kB/s，那 1% 是测量窗口边界的在途
字节，不是丢包——以 `uart` 模式的精确计数为准。

> **别把线上时间减掉当成"USB 慢"**：64 字节 chunk 的 746 us 里有 694 us 是 UART 线上
> 时间。非线上那 50~96 us 与 CAN 路径的约 100 us 同量级，是同一条 USB 路径。

## 8. 此前各轮积累的结论（从会话记忆整理，本轮做了确认或修正）

这一节把散落在会话记忆里的既有结论收进文档，并标注本轮的确认/修正。

### 8.1 主机侧调优：哪些有效、多少

| 杠杆 | 效果 | 状态 |
|---|---|---|
| **固件 `release` vs `debug`（-O3 vs -Og）** | **板级 p50 约 20 us** | **比所有主机旋钮加起来都大**。怪主机之前先确认固件构建类型 |
| **xHCI 中断线程在 P 核 vs E 核** | **p50 约 21 us**（100.3 vs 121.4） | 必须读 `effective_affinity_list`，不是 `ps` 的 psr |
| governor=performance | 1 kHz 下 p50 16~18 us | gap=0 看不见（见 6.x）。**TL101 上值 0**：`isolcpus` + SCHED_FIFO 已经把频率顶住，governor 成了无关变量。真正的要求是"必须有东西顶住频率"，两者有其一即可（`HOST_TUNING.md` 11.3、11.11.3）`[实测 2026-09-05]` |
| 事件线程绑 P 核 | 不绑时 p99.9 176 / max 458 | 绑核比隔离重要得多 |
| 多板共享 IRQ 提到 FIFO 90 | max 190~222 -> 126~141 us | 单板是 no-op。**需要竞争负载才成立**：中断核上没有别的 RT 线程时，双板下提到 FIFO 95 实测为 0（`HOST_TUNING.md` 11.11.3）`[实测 2026-09-05]` |
| `--pmqos` | **1 kHz 下 p99.9 −9 us**（本轮实测） | 此前记为"只值 2 us"，是 gap=0 测的，已更正 |
| isolcpus 隔离整个物理 P 核 | p99 约 1.5 us，p99.9 −5~13 us | 代价一整个 P 核，本机最终**不用** |

**实测无效**：per-core C-state disable、C6/C10 全关留 C1E、teo governor、btusb 解绑。
**实测有害**：xHCI 中断绑到事件线程同核（p50 124.8 -> 146.2）。

### 8.2 延迟分解：约 99 us 的 p50 花在哪

- **CAN 线上时间 50.3 us（51%）**，纯加性：FD min 85.7（线上 50.3）vs classic min 149.5（线上 117），差值 63.8 与预测 66.7 相符
- 固定非 CAN 部分约 27~34 us（USB 下行 + 唤醒 + 一次性固件开销）
- 微帧量化/抖动约 22 us
- **固件不在关键路径上**：一个 USB 包里发 8/16 帧，稳态步进 51.7~51.8 us，只比线上时间多 1.4 us。**板端 C++ 优化总共只有约 1.4 us 余量**

**所以剩余空间在 CAN 位时序，不在主机也不在固件。** 每帧 50.3 us 里约 30 us 是 1 Mbit
仲裁段；仲裁 1M->2M 约值 15 us `[估算，未测]`，但两端必须同时重算采样点。

### 8.3 协议的结构性限制：8 字节 DLC

`required_can_size()` 强制 `can_data.size() <= 8`，DLC 只有 3 bit，**协议载不动 CAN-FD
的 64 字节**。载荷带宽因此是 19870 x 8 B ≈ 155 KB/s，而 5 Mbit 数据段能跑 625 KB/s
（约 25% 效率）。

**但不要"顺手把 DLC 扩到 64"**：M_CAN 的元素大小按**最大**载荷配置，8 字节时 16 B/元素、
64 字节时 72 B/元素，同样 RAM 下 RX FIFO 和 TX buffer 从 32 个掉到 8 个。这不是 STM32
的怪癖——STM32H7 FDCAN 和 HPM MCAN 是同一个 Bosch M_CAN IP。仓库两块板都是**故意**保持
8 字节元素同时让控制器常驻 FD 模式（"严格超集"）。

FIFO 深度影响的是**突发容忍和丢帧，不是延迟**。32 个元素在 19870 f/s 下是约 1.6 ms 缓冲。

### 8.4 硬件事实

- **两块板永远落在 bus 3**：雷电控制器（`00:0d.0`）有自己的 xHCI，但它的 USB 2.0 根端口
  ACPI 标 `connect_type = not used`，**物理上没接线**。HPM5321 只有 USB 2.0 HS，
  所以全部落到 PCH 的 `00:14.0`。**这台笔记本上无解**，换控制器需要扩展坞或另一台机器
- **`irqaffinity=` 保护不了隔离核**：多队列驱动运行时会 `irq_set_affinity_hint` 把队列
  放回去。nvme 的 blk-mq per-CPU 中断**根本改不了**

### 8.5 采样点与版本偏斜

"classic CAN 通、CAN-FD 单向不通"是采样点不一致的特征签名——**但两块板跑不同固件提交
也会产生一模一样的现象**。多板 rig 上遇到 FD 单向时，**先 `lsusb -d a511:5322 -v | grep
iProduct` 确认所有板版本一致**，再去读寄存器遥测。

### 8.6 工具与工作流的坑

| 坑 | 怎么做 |
|---|---|
| `.scripts/clang-format-check --fix` | **不接受路径参数，会重写全仓库约 167 个文件**，包括有未提交改动的。只格式化自己的文件：`clang-format -i --style=file:.clang-format <file>` |

## 11. EP0 并发请求的代价 [实测 2026-09-05]

**结论先行：偶发的 EP0 vendor 请求对 bulk 包率是免费的。真实的 keepalive 频率
（4 Hz）测不出影响；到 1 kHz 仍在 1% 以内；4 kHz 才掉 3.3%。所以"EP0 上再加一条请求会
不会拖慢数据面"这个顾虑，在 kHz 以下不成立。**

起因是一个设计问题：协议 session（`kSession`）该留在 bulk 流里，还是搬到 EP0 上去。
性能只是其中一个判据，先把它测掉。

工况：两块 HPM5321 双 CAN 板，`usb_packet_rate` 的 **uartonly** flood（唯一不被 CAN 线速
限住、能测出端点上限的模式），**同一个板对象会话内交替**跑各档，6 s 一块、4 轮。EP0 激励
是 `board.can_status(CanPort::kCan1)`，即一条 `kGetCanStatus`。全部送达：`ep0_fail=0`，
实际次数等于请求次数。

| EP0 频率 | packets/s（4 块中位数） | 相对对照 |
|---|---|---|
| 0（对照） | 63566 | — |
| **4 Hz**（`kSessionRefreshInterval` = 250 ms） | 63545 | **−0.03%** |
| 100 Hz | 63239 | −0.51% |
| 1000 Hz | 63088 | −0.75% |
| 4000 Hz | 61477 | **−3.29%** |

判读要点：

1. **4 Hz 是"测不出"，不是"很小"。** 对照块自己散布 0.58%（63357~63727），差值埋在里面。
2. **100 Hz 以上是真的**，判据不是幅度而是**排序完全分离**：四个 100 Hz 块全部低于四个
   对照块，四个 1000 Hz 块又全部低于 100 Hz 块。
3. **代价对频率不是线性的。** 100 Hz 掉 327 包/s，1000 Hz 才掉 478——有一块固定开销来自
   "激励线程在跑"本身（主机 CPU 争用），不全是总线时间。**别拿单点外推。**
4. 这是最敏感的工况。生产路径上 CAN 线速占掉 58% 的预算，连 4 kHz 那一档都不会露头。

工具：`usb_packet_rate.cpp` 加一个激励线程和块交替（scratchpad `ep0_cost_test.cpp`，未入库）。
交替是硬要求，理由见第 6 节：同一份镜像的包率跨时间会漂 5%。
