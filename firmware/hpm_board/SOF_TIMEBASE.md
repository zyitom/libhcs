# 跨板时间轴：USB SOF / FRINDEX 验证

> **文档类型**：过程记录（实测验证）
> **适用范围**：`firmware/hpm_board/`，HPM5321 / HPM6E8Y 的 USB 数据固件；多块板挂同一个 USB 主机控制器的场景
> **状态**：现行有效（第 1 步验证、第 2 步共享时间轴、第六条直接实测均已上板；"在第 k 微帧执行"的动作层未实现）
> **相关文档**：[AGENTS.md](AGENTS.md)（板级现行规范） · [CONTROL_TIMING.md](CONTROL_TIMING.md)（这条轴在控制环里到底用不用得上） · [../../HOST_TUNING.md](../../HOST_TUNING.md)（主机侧调优） · 固件 `app/src/sync/sof_probe.hpp` · 主机工具 `host/examples/sof_probe.cpp`

## 摘要

多块 HPM 从机板经 USB 直连同一台工控机，要让它们共用一条时间轴做协同电机控制。方案
把时间轴拆成两个来源：**FRINDEX**（硬件被动跟随主机 SOF，精度高但 2.048 s 回绕）
与**上位机时间戳**（毫秒级，只用来定圈数）。整套方案成立的前提是"FRINDEX 每个 SOF
恰好加一，且各板数值相同"——本文记录这条前提的上板验证结果与复现方法。

**第 1 步结论：前提成立，且比预期干净。** 稳态下 delta 恒为 1（两块板各 47.9 万次
转换，100.00000%），不存在"SRI 标志先置位、FRINDEX 后递增"的竞态，两块板计到的微帧
数一致。

**同步精度：跨板 1 sigma 0.042 us、3 sigma 约 0.13 us**（时间轴本身，不含动作层）。
**这是推导值**——由四个各自实测的分项合成（见 5.2），**不是端到端实测**。直接实测试过六条路，
前五条全部失败并已定位根因；**第六条（GPTMR 脉冲交换）在 2026-08-20 跑通**，实测
**跨板 skew 1 sigma 约 20 ns、通路延迟 129 ns**，比推导值更好且与单板残差互相印证，
全部记在第 5.4/5.5 节，**结论是错的一直是"尺子"不是时间轴**。

**第 2 步结论：两块板落在同一条绝对时间轴上，圈数零分歧。** 大计数器 + 滑动窗口拟合
+ 圈数状态机已实现并上板，锚点搭在**既有的 session 包**上。30 s 内 119 次上报全部
`valid`、运行期异常 0、圈数错配 0。主机侧另有一条到 Unix 时间的映射，见第 5 节。
第 3 步（"在第 k 号微帧执行"的动作语义与提前量）尚未实现。

## 1. 验证做了什么

固件 `app/src/sync/sof_probe.*`（开关 `-Dlibhcs_SOF_DIAG=ON`）在 USB0 中断向量的
**最前面**、进 TinyUSB 的 `dcd_int_handler()` 之前挂一个钩子：`USBSTS.SRI` 置位时
立刻读 FRINDEX、读本地 mchtmr、再读一次 FRINDEX，然后 W1C 掉 SRI。记录：

- 相邻 FRINDEX 差值的完整直方图（0..8 各一档，≥9 一档）；
- **同一次中断内的第二次 FRINDEX 读数**——它与第一次不同，就是"采样点正好压在递增沿"
  的直接签名；
- **ISR 到 ISR 的本地定时器间隔**——差值为 1 但间隔是 250 us，说明丢了中断而直方图
  看不出来，只有这一列能看见；
- 每个异常差值附带当次中断的 `USBSTS`、`PORTSC1`（端口速度 / 挂起 / PHY 低功耗）和
  本地时间戳。

SRI 标志在钩子里就被消费掉，所以 TinyUSB 完全看不到 SOF，不会每微帧往事件队列塞一条
`DCD_EVENT_SOF`——**开着这个探针的固件，其 USB 行为与不开时一致**。

主机侧 `host/examples/sof_probe.cpp` 同时打开所有在线板子解码遥测，并做跨板比对。

## 2. 结论与数据 [实测 2026-08-19，两块 HPM5321，同一 xHCI（Bus 003 port 1/2）]

### 2.1 稳态：delta 恒为 1，没有竞态

60 s 空载：

| | 板 AF-90A7 | 板 AF-958F |
|---|---|---|
| delta == 1 | **479161 / 100.00000%** | **479162 / 100.00000%** |
| delta != 1 | 0 | 0 |
| 中断内 FRINDEX 变动 | **0** | **0** |
| 含异常的 100 ms 周期 | 0 / 599 | 0 / 599 |
| ISR 间隔 us | min 123.250 / mean 125.0102 / max 126.750 | min 123.500 / mean 125.0101 / max 126.500 |

45 s + 每板 18000 包/s 的 CAN-FD 负载（两块板互发，走各自的 USB 下行）：

| | 板 AF-90A7 | 板 AF-958F |
|---|---|---|
| delta == 1 | **359171 / 100.00000%** | **359171 / 100.00000%** |
| 中断内 FRINDEX 变动 | 0 | 0 |
| ISR 间隔 us | min 121.000 / mean 125.0102 / max 129.000 | min 121.750 / mean 125.0101 / max 128.250 |

**"0 / 2 交替"一次都没出现，delta 2 在稳态下计数为零。** 原设计文档里"未验证前不要
展开后续开发"的那个竞态，在这颗芯片这条路径上不存在，读取顺序不需要补偿策略。
`[实测]`

**两块板计到的转换次数完全相同**（空载 479161 vs 479162，负载 359171 vs 359171）——
这不是巧合，是"同一串 SOF 边沿"的直接体现。

### 2.2 本地晶振相对 USB 时钟慢约 0.008%

ISR 间隔均值 **125.0102 us**（理想 125.000），两块板一致到小数点后第四位。这就是
方案里滑动窗口线性拟合要跟踪的温漂量级：约 +82 ppm 的固定偏差，加上 ±4 us 的中断
进入抖动（负载下 121.0~129.0）。**拟合把抖动压下去，偏差由拟合斜率吸收。** `[实测]`

### 2.3 唯一的异常全部在枚举窗口内，且是确定性的

自举计数里确实有 delta 0（板 A 977 次、板 B 1320 次），但：

- **全部发生在会话建立之前的同一个毫秒刻度**，稳态 599 个周期里一个都没有；
- 当时 `PORTSC1 = 0x10000885`，解出来是 **full-speed、suspended、port-enable-change**，
  `FRINDEX` 钉在 `0x0000`，中断间隔 1000 us（整帧，不是微帧）；
- 同一块板重启后计数一模一样（板 A 两次都是 977），是确定性的枚举序列。

**含义：这是"总线还没跑起来"，不是"计数器坏了"。** 方案里"无效 → 等待时间戳 →
有效"的状态机本来就覆盖这段——上电后时间轴本就无效，直到上位机下发第一条时间戳。
枚举窗口不需要额外处理。`[实测]`

> 探针第 1 版的异常环每周期只存 8 条，全被枚举窗口填满，之后的稳态异常一条都没记上，
> 打印出来的全是自举假象。第 2 版把端口状态与时间戳放进条目、容量提到 12，主机侧改成
> **以第一条记录为基线做差**，才把稳态从自举里分离出来。**累计计数器不做差就没有稳态。**

### 2.4 跨板一致性

主机把每块板的记录按到达时间配对，算
`(frame_i - frame_0) - (到达时差 / 125 us)`：

| | 残差（微帧） |
|---|---|
| 空载 60 s，n=600 | min -1 / p50 **0** / max 3 |
| 负载 45 s，n=450 | min -3 / p50 **0** / max 4 |

残差中位数为 0、无漂移。**这个量的分辨率受限于遥测上行的传输抖动（约几十 us），
所以它只能证明"两块板数的是同一个计数器"，不能用来标定亚微秒精度**——后者要等第 2 步
的拟合上线后，用"在第 k 号微帧执行"的实际动作去测。`[实测]`

## 4. 共享时间轴的实现 [实测 2026-08-19]

### 4.1 锚点为什么搭在 session 包上

原方案建议"独立端点或独立包类型"。实际做法是**扩展既有的 session 字段**，理由有三，
都不是省事：

1. session 是链路上**唯一一条已经存在的、周期性的、与数据面无关**的交换（主机
   keepalive 线程 250 ms 一轮，`host/src/protocol/handler.cpp`），锚点的节奏要求与它
   完全一致；
2. 锚点必须**与会话同生共死**。板子丢了主机却留着一条时间轴，是最危险的状态——主机
   回来后可能以为它仍然对齐。挂在 session 上，nonce 校验和租约到期天然覆盖这件事；
3. 板子的状态回报可以搭同一次往返（`kTimeAnchor` -> `kTimeStatus`），主机因此**免费
   拿到往返时延**，中点即采样时刻，USB 传输偏置基本抵消。

新增两个 `SessionType`（`kTimeAnchor = 4`、`kTimeStatus = 5`）。**它们在 session 头
之后带载荷，所以不认识它们的旧固件无法跳过**，会把载荷当成下一个字段而丢帧。因此主机
侧是**显式开关**：`AdvancedOptions::set_enable_time_sync(true)`，默认关。

### 4.2 圈数怎么定，以及为什么主机时钟不准也不会破坏同步

板端计数器**用第一次读到的 FRINDEX 播种**，此后 `counter mod 16384 == FRINDEX` 恒成立。
主机只送一个估计值，板子做的是：

```
absolute = counter + 16384 * round((host_estimate - counter) / 16384)
```

即**只从主机拿"第几圈"，低 14 位始终来自硬件**。于是：

- 主机估计误差要超过 **±1.024 s** 才会改变任何一块板的结果；
- 两块板拿到同一个估计值时，因为低 14 位相同，**必然算出同一个绝对值**；
- 更强的一条：**即使主机估计得离谱，各板之间仍然一致**，错的只是绝对值。
  **绝对正确性依赖主机时钟，跨板一致性完全不依赖。** 这就是"并联而非串联"的实质。

代价是主机的估计轴必须**全进程唯一**（`host/include/libhcs/time/timeline.hpp` 是单例）。
每块板一个原点会让各板各自自洽、互相差整秒——这是最难发现的失败形态。

### 4.3 拟合与状态机

板端 128 个样本、每 64 微帧取一个，窗口 8192 微帧（1.024 s），512 字节 RAM。ISR 只做
一次存储；最小二乘在主循环里跑（20 ms 一次，屏蔽中断约 1 us 拷贝环形缓冲）。斜率用
Q16 定点（1 ppm 在 5 ms 提前量上是 5 ns），相位取整到 1 tick = 0.25 us。

状态机 `kInvalid -> kWaitingAnchor -> kValid`，异常处理按原方案分档：

| delta | 处理 |
|---|---|
| 1 | 正常 |
| 2~7 | 计数照补（计数器仍然正确），但**丢弃整个拟合窗口** |
| 0 或 >=8 | 计数器不可信，**宣布失效**，等下一个锚点 |
| 锚点解出的圈数与当前不同 | **宣布失效**，不静默接受 |

### 4.4 实测结果

两块 HPM5321，`-Dlibhcs_TIME_SYNC=ON`，30 s：

| | 板 AF-90A7 | 板 AF-958F |
|---|---|---|
| 上报 / valid | 119 / 119 | 119 / 119 |
| 运行期异常 | **0** | **0** |
| 状态跳变 | 0 | 0 |
| 拟合出的本地 tick/微帧 | 500.0410 | 500.0400 |
| 换算晶振偏差 | **+81.9 ppm** | **+80.0 ppm** |

晶振偏差与第 2.2 节独立测到的 125.0102 us（+82 ppm）一致——两条互不相干的路径给出
同一个数，是拟合正确的旁证。

**跨板绝对微帧一致性**：残差 min -1 / p50 **0** / max 3 个微帧，**圈数错配 0 次**。
残差量级由 USB 上行抖动决定（几十 us），所以它证明的是"两块板数的是同一个绝对微帧"，
亚微秒那一层由第 2 节的硬件计数器保证，与本节无关。

### 4.5 开销：测不出来 [实测 2026-08-19，交错 3 轮]

打开时间轴等于给板子加 8 kHz 的 SOF 中断，本仓库对这种事一向要求实测。
`dual_board_test latency 0 5000`，`HCS_LATENCY_GAP_US=1000`，同一台主机、同一副线，
两个镜像交错烧录各 3 轮：

| | p50 | p90 | p99 |
|---|---|---|---|
| `TIME_SYNC=OFF` | 133.3 / 134.0 / 133.4 | 154.6 / 155.6 / 152.3 | 174.4 / 176.1 / 175.0 |
| `TIME_SYNC=ON` | 132.7 / 131.3 / 132.6 | 154.9 / 151.5 / 152.3 | 176.5 / 173.1 / 173.8 |

**两组区间完全重叠，差异在本机约 1~2 us 的轮间离散度之下**。注意这台主机**没有跑
`host-tuning.sh`、也没有 `chrt`**，所以绝对值比 AGENTS.md 里记录的 p50 100.6 差不少，
尾部还有约 1 ms 的毛刺；这里只用它做 A/B，不能当作绝对性能引用。
**结论：8 kHz SOF 中断的代价在这条链路上测不出来** `[实测]`；要更细的判据得先调好主机
再重测。

### 4.6 时钟树：精确定时必须待在 COMMON 组挂晶振 [手册 + 代码]

这是本轮最耐用的一条判据，第 5.4 节全部失败的根因都在这里。

```c
// boards/hpm5321/board.c
clock_set_source_divider(clock_mchtmr0, clk_src_osc24m, 6);   // 24MHz 晶振 ÷6 = 4MHz

// soc/HPM5300/HPM5361/hpm_clock_drv.h
clock_mchtmr0 = MAKE_CLOCK_NAME(..., CLK_SRC_GROUP_COMMON, ...)  // 组里有 clk_src_osc24m
clock_gptmr0  = MAKE_CLOCK_NAME(..., CLK_SRC_GROUP_COMMON, ...)  // 同上
clock_ptpc    = MAKE_CLOCK_NAME(..., CLK_SRC_GROUP_AHB,   14)    // 只能吃 PLL0
pllctlv2_init_pll_with_freq(HPM_PLLCTLV2, pllctlv2_pll0, 960000000);
```

而数据手册 1.2.4 节写着：**"2 个锁相环 PLL，支持小数分频，支持展频"**。展频是为压 EMI 故意
周期性调制 PLL 频率，典型幅度 ±0.5~1%。

| 外设 | 时钟路径 | 实测稳定性 |
|---|---|---|
| MCHTMR | 晶振 ÷6，**不过 PLL** | 两块板差 **1.8 ppm** |
| PTPC | AHB 组 → PLL0（小数分频 + 展频） | 两块板差 **143 ppm**，板内还漂几百 ppm |
| GPTMR | COMMON 组，**可选晶振** | 可做到与 MCHTMR 同级 |

**判据：`CLK_SRC_GROUP_COMMON` 的外设可以直接挂 `clk_src_osc24m`；`CLK_SRC_GROUP_AHB` 的只能
吃 PLL0。任何要精确定时的东西都必须待在 COMMON 组并挂晶振。**

PTPC 漂**不是缺陷**——它是 IEEE 1588 模块，本来就设计成被驯服的时钟
（`ptpc_set_ns_counter_step` 细调增量）。我错在把一个"该被驯服的时钟"当成"自由跑的参考"。
它对"给 CAN 帧打相对时间戳"（原设计用途）完全够用。

### 4.7 芯片自带的硬件同步能力（已验证可用，未接入）

查 `hpm_trgmmux_src.h` 发现**这件事芯片本来就有硬件支持，我一直在用软件绕**：

```c
HPM_TRGM0_INPUT_SRC_USB0_SOF        (0x3)   /* USB0 frame start */
HPM_TRGM0_OUTPUT_SRC_MCAN_PTPC0_CAP (0x2E)  /* PTPC input capture 0 */
HPM_TRGM0_INPUT_SRC_PTPC_CMP0       (0x4)   /* PTPC output comparison 0 */
```

**触发矩阵可以把 USB SOF 直接接到 PTPC 的输入捕获**——每个微帧硬件锁存，软件完全不参与。
已上板验证在工作（诊断量"计数器减捕获值"读出的就是中断进入延迟）。

而 `PTPC_CMP0` 作为 TRGM **输入源**，意味着 PTPC 比较到点可以直接触发别的外设，**CPU 不参与
——这就是 EtherCAT DC 里 SYNC0 的等价物**，是动作层该用的东西。

**这条路的正确用法**（未实现）：用 TRGM 硬件捕获把 PTPC 锁到 SOF 上，**驯服它**而不是拟合它；
PTPC 一旦对齐，CAN 硬件时间戳**直接落在共享时间轴上，不需要任何换算**——第 5.4 节那五个坑会
整个消失。

## 5. 同步精度怎么测

**结论先行：时间轴本身的跨板偏差 1 sigma 0.042 us，3 sigma 约 0.13 us，比 ~1 us 的目标
好一个数量级。但这个数**不含动作层**——"在第 k 微帧真的动一下"的偏差还没测，因为动作层
还没实现。`[实测 2026-08-19，两块板 60 s]`

### 5.1 为什么不能拿第 4.4 节那个残差当精度

第 4.4 节的跨板残差（p50 0 微帧）是**主机侧**比对两块板的上报算出来的，分辨率被 USB
上行抖动（几十 us）钉死在**一个微帧**的量级。它能证明"圈数没错、数的是同一个计数器"，
**证明不了微秒**。想测微秒必须换一个测法。

### 5.2 正确的测法：误差只可能在拟合里，而拟合误差单板就能测

误差来源可以逐条排掉：

| 环节 | 跨板是否引入偏差 | 依据 |
|---|---|---|
| SOF 边沿本身 | 否，同一个主机控制器广播 | 硬件 |
| 微帧计数器 | 否，delta 恒为 1，两板转换次数相同 | 第 2.1 节 |
| 圈数（锚点） | 否，错配 0 次 | 第 4.4 节 |
| **微帧 -> 本地定时器刻度的拟合** | **是，唯一来源** | 本节 |

所以：

```
跨板偏差 = A 的拟合误差 - B 的拟合误差
```

而**拟合误差在单板上就能测**，不需要示波器、不需要跨板比对：每个降采样样本先用**当前
已发布的拟合**（在这个样本存在之前就算好的）预测一次，再放进窗口。预测值减实测值就是
**货真价实的外推误差**，正是被调度的动作会遇到的那一个。

### 5.3 三个统计量要分清，别看错

每条上报已经带了约 33 个样本的**均值**，所以中断抖动在它里面被压了 sqrt(33)：

| 统计量 | 含义 | 实测 |
|---|---|---|
| 各报均值的**均值** | **系统性偏置**。最小二乘天然把它压到 0，非零才说明有问题 | -0.0010 / -0.0020 us |
| 各报均值的**离散度** | **真正的品质因数**：板子对"现在"的认知在两次上报之间漂多少 | 1 sigma **0.038 / 0.016 us** |
| 单个样本的最大值 | **中断抖动**，不是时间轴误差 | 1.29 / 2.47 us |

**最后一行最容易看错。** 被调度的动作是靠定时器比较触发的，不从 SOF 中断里出来，
所以它根本不付这 1~2 us。把它当成精度会低估一个数量级。

跨板合成（两块板独立，方差相加）：**1 sigma 0.042 us，3 sigma 约 0.13 us。**

### 5.4 直接实测：五次尝试，全部失败，但每次都定位到一个真实缺陷

**结论先行：直接实测跨板 σ 至今没有做成。第 5.2/5.3 节那个 42 ns 仍是唯一能引用的数字，
它是四个各自实测的分项合成的推导值。** 本节记录五次尝试，因为**每一次的失败原因都是一条
可复用的判据**，而且它们共同证明了一件事：错的一直是"尺子"，不是时间轴。

思路都一样：让两块板对**同一个物理事件**各打一个硬件时间戳。用的事件是 CAN 总线上的一帧
——四个 CAN 口并到一条总线上（用户的分电板），一帧发出去，**每个其他控制器都会捕获它**，
包括发送板自己的第二个控制器。

#### 关键的对照组，以及它的盲区

同一块板的两个控制器给同一帧打戳，差值应该是零——它们共用同一个 PTPC。实测确认：

```
board B, CAN0 vs CAN1   n=4000   mean -0.4 ns   sigma 2.8 ns   范围 ±13.4 ns
```

±13.4 ns 正好是 **±2 个 PTPC 步进**（6.25 ns）。**这证明测量手段本身的分辨率是个位数 ns，
远好于要验证的 42 ns。**

> **但这个对照组对"换算错误"是瞎的。** 同一帧的两个戳走**同一次换算**，换算的误差在差值里
> 整个抵消。我差点因此认为换算是对的。**对照组干净 ≠ 换算正确**，这是本节最容易踩的坑。

#### 五次尝试

| # | 做法 | 错在哪 | 跨板结果 |
|---|---|---|---|
| 1 | 假设 PTPC:mchtmr = 精确 240，只用指数平均跟踪偏移 | **指数平均对任何有残余斜率的量都会滞后**（时间常数 × 斜率）；而假设的比例不够精确，斜率不为零 | 均值 **452 µs** |
| 2 | 改成对微帧计数器做第二次最小二乘 | `sec*1e9+ns` 组合了**两个不同步锁存的寄存器**，读者无法构造相干配对 | 均值 **2.6 µs** |
| 3 | 只读 ns 寄存器，全部差值走模运算 | 软件在 ISR 里读 PTPC，**带 ±1~2 µs 中断抖动**；且 PTPC 挂 PLL0 自己漂几百 ppm，**外推 28 ms 就错 14~22 µs** | σ **30 µs** |
| 4 | TRGM 硬件捕获 + 相邻 SOF 之间内插 | SOF 历史**记在降采样之后**，内插跨度变成 8 ms 而不是 125 µs——把硬件捕获刚赢回来的精度原样还了回去 | σ **8 µs** 带宽 |
| 5 | 历史改成全速率 + 捕获归属按微帧四舍五入 | 归属推断的**前提不成立**（见下） | 未完成 |

**第 2 次的教训值得单独记**：`ptpc_get_timestamp_second()` 和 `ptpc_get_timestamp_ns()` 是
两个寄存器，**不是同一拍锁存的**。我写的"读 ns、读 sec、再读 ns"防翻转循环防不住这个——它
只能挡住"翻转发生在两次读之间"，挡不住"两个寄存器本来就不属于同一时刻"。**正解是根本不读
秒寄存器**：换算只需要相对参考点的差，而这个差永远 < 30 ms，远小于 ns 计数器 1.04 s 的
翻转周期，模运算就够。

**第 4 次的教训**：内插的跨度 = 历史的采样间隔。**把历史记在降采样分支后面，等于把内插退化
成外推。**

#### 第 5 次卡在哪：捕获相位是随机的

TRGM 硬件捕获**确认在工作**——诊断量是"自由运行计数器减去锁存值"，即中断进入延迟：

#### 为什么这些都没有牵连到 42 ns

有人会问：采样相位乱了，机器定时器那条路是不是也废了。**没有**——它的外推残差是独立统计的，
实测 **均值 0.001 µs / 离散度 0.038 µs**。如果它的采样相位真在 125 µs 范围内乱跳，这个残差
不可能是这个数。

**这些失败全部发生在"PTPC 时刻 → 微帧轴"这条只为测量而存在的路上。把它整个删掉，时间轴照常
工作。**

### 5.5 第六条路：GPTMR 硬件脉冲交换（已上板，跑通）

放弃 PTPC，理由不是偏好而是时钟树（见 4.6 节）：

```c
clock_gptmr0 = MAKE_CLOCK_NAME(..., CLK_SRC_GROUP_COMMON, ...)   // 可挂 clk_src_osc24m
clock_ptpc   = MAKE_CLOCK_NAME(..., CLK_SRC_GROUP_AHB,    14)    // 只能吃 PLL0
```

**GPTMR 可以直接挂 24 MHz 晶振**，不经 PLL0，就没有小数分频和展频——这才是选它的理由。

> **原文这里还写过"3000 tick/微帧是精确值不是估计"，这句是错的，2026-08-20 更正。**
> 微帧轴是**主机**的 USB 时钟，GPTMR 数的是**本板**晶振，两个独立振荡器。第 2.2 节自己
> 实测过这两者差约 **+80 ppm**，所以真值是约 **3000.245 tick/微帧**。按 3000 算，50 ms
> 的提前量就会引入 **98 tick ≈ 4.1 us** 的系统误差；两块板 ppm 不同（81.9 / 80.0），
> 双向差分也只抵掉共模的那部分，残差随提前量线性增长。**因此比例必须拟合，不能假设**，
> 现在 `pulse.cpp` 用与 timebase 相同形状的窗口（128 样本 x 64 微帧 = 1.024 s）拟合它。
> `[实测 2.2 节 + 推断]`

**不用加线**：UART0 那两根线本来就交叉互联，而两个引脚就是 GPTMR0 通道 1 的比较/捕获脚：

| 引脚 | 原用途 | ALT1 |
|---|---|---|
| PB08 | UART0 TXD | `GPTMR0_COMP_1` 比较输出 |
| PB09 | UART0 RXD | `GPTMR0_CAPT_1` 捕获输入 |

**接线在 2026-08-20 已经独立验证过**：刷脉冲固件之前先跑
`./host/build/examples/dual_board_test link`，`A.UART0 -> B.UART0` 与 `B.UART0 -> A.UART0`
双向 PASS（`rx_bytes=16`）。**先证明那根线是通的，再把它改成定时链路**——否则测不出脉冲时
分不清是时基错还是线断。`[实测]`

双向硬件比较→捕获，两端都没有 CPU。双向对打让恒定的通路延迟抵消：

```
skew = ((b_rx - a_tx) - (a_rx - b_tx)) / 2
```

分辨率 1 tick = 41.7 ns，看着比 42 ns 目标粗，但**粗得无害**：量化零均值、被真实抖动 dither，
跑上千次均值收敛到亚 ns，σ 只按平方相加涨到 44 ns，可以反卷积掉。

#### 2026-08-20 这一轮补了什么

主机侧的缺口已经全部补齐，固件侧则修掉了三个**必然让测量失败**的缺陷：

| 位置 | 问题 | 修法 |
|---|---|---|
| `pulse.cpp` `bring_up_hardware()` | **漏了 `clock_add_to_group(clock_gptmr0, 0)`**，GPTMR0 被时钟门控，第一次写寄存器就把核卡死 | 补上；SDK 自己的 `init_gptmr0_clock()` 就是这一行 |
| `pulse.cpp` `schedule()` | 只写 CMP0。比较输出是"CMP0 拉高、CMP1 拉低"，CMP1 停在 `0xFFFFFFFF`，所以**第一发之后引脚一直是高**，再匹配也没有边沿 | 每轮同时写 CMP0 与 CMP1（脉宽 10 us） |
| `pulse.cpp` 时刻换算 | 用"最新一条 SOF 记录 + 3000 整数外推"定目标，等于把**那一条**中断的 ±0.5 us 抖动原样打进脉冲，比被测量大一个数量级 | 改成 1.024 s 窗口拟合（斜率用两半均值差，相位用全窗均值），捕获侧用同一条直线求逆，不再做相邻两点插值 |
| `host/src/protocol/handler.cpp` | `Handler::send_pulse_schedule` 只有声明没有定义 | 补定义 + `Hpm5321::send_pulse_schedule` 转发 |
| 协议 | 报文只在**捕获时**才发，主机分不清"板子没武装"和"武装了但没听见" | `PulseReportPayload` 加一字节 `Flags`（`kPulseArmed` / `kPulseCaptured`），**每收到一次 schedule 就回一条**（见 `core/include/libhcs/data/datas.hpp`） |
| 主机工具 | 没有 | `host/examples/pulse_skew_test.cpp`，按 7.1 的顺序分三段输出 |

#### 上板结果：跨板 skew 1 sigma 约 20 ns，通路延迟 129 ns [实测 2026-08-20]

**这是这条时间轴第一次端到端实测**，而且比第 5.2 节推导出的 42 ns 更好。两块 HPM5321，
`pulse_skew_test 400 400`（提前量 50 ms），稳态连测：

| 轮次 | 通路延迟 均值 / sigma | skew 均值 | skew sigma |
|---|---|---|---|
| 1（重刷后第一轮，含重新锚定暂态） | 128.7 / 15.5 ns | +17.3 ns | 50.8 ns |
| 2 | 130.0 / 13.3 ns | +6.5 ns | **19.4 ns** |
| 3 | 129.0 / 13.6 ns | +9.8 ns | **22.7 ns** |

**怎么读这三个数：**

- **通路延迟 129 ns 是常数，不是 skew。** 它是单向的电缆 + pad + 施密特触发器，五次运行
  给出 128.7 / 130.0 / 129.0 / 129.7 / 128.8 / 130.8，离散度 1 ns。它以**相同符号**进入
  两块板的报告，所以在双向差里整个消掉——出现在"和的一半"里，不在"差的一半"里。
- **跨板 skew 稳态 1 sigma 约 20 ns，3 sigma 约 60 ns。** 量化底是 8.5 ns
  （单次捕获 41.7/sqrt(12) = 12 ns，双向取半再除 sqrt(2)），所以这 20 ns 里大部分是真实的，
  不是尺子。
- **均值那几纳秒是真实的固定不对称，不是斜率误差**——判据是提前量扫描：12.5 / 100 / 250 ms
  下 skew 均值 +3.1 / +6.9 / +4.4 ns，**不随提前量放大**；若是拟合斜率误差，250 ms 上应当
  放大 20 倍。同一组数据还顺带标出了斜率不确定度：延迟的 sigma 从 12.8 涨到 23.5 ns，
  对应约 **0.1 ppm**。

**与既有推导互相印证（两把独立的尺子）**：把 skew sigma 20 ns 按"两块板的相位误差独立、
在差里各占一半"折回单板，是约 14 ns；同一天 `time_sync_test` 报的单板拟合外推残差离散度是
**17 ns**（0.0173 us）。一个是硬件脉冲对打、一个是纯软件的样本外残差，**两者从未共用任何
代码路径，却给出同一量级**。第 5.2 节那个 42 ns 是保守侧的推导值，现在有了实测的上界。

**仍然要说清的边界**：这测的是"两块板各自按共享轴发一个**硬件比较输出**时，实际动作差多少"。
它已经包含了各板的拟合相位误差（动作层真正要付的那部分），但**不包含**任何软件动作路径
——若动作是在中断里写寄存器，还要另加那条路径的抖动，见 5.6。

#### 教训：实验性模块不要在 boot 路径上碰硬件 [实测 2026-08-20，代价是两块板]

**结论先行：这块板的 app 一旦在 USB 枚举前卡死，就只能靠拉 PA07 到 GND 或 JTAG 救回来，
所以任何没上过板的初始化代码都不该跑在 `App::init()` 里。**

`pulse::init()` 当时在 `App::init()` 中无条件执行，而它漏了资源组那一行。三件事叠在一起
就是砖：

1. HPM 的外设时钟门控关着时，写寄存器**不报错也不返回**，AHB 事务永远不完成，核就停在那；
2. 卡死发生在主循环之前，USB 从来没枚举，**DFU-RT 接口也就不存在**；
3. `BOARD_BOOTLOADER_MODE=auto` 的 bootloader 看到一份**校验合法**的 app 就直接跳进去，
   不给 DFU 窗口；而这块板没有按键（PA07 复用 JTAG_TMS，只有复位后 4x250us 的采样窗口）。

修法有两层，缺一不可：**补上 `clock_add_to_group`**（治本），以及**把整个硬件 bring-up
推迟到第一次收到 host 的 schedule 请求**（治标但更重要）。后者的意思是：这条路上再出任何
问题，前提都是"USB 已经枚举、session 已经建立"，于是烧录通道始终活着，故障从"变砖"降级成
"诊断功能不工作"。`pulse::init()` 现在是空函数，注释写明了为什么空。

> **推论，适用于所有诊断开关**：`-Dlibhcs_*` 系列里凡是会碰时钟树、引脚复用或中断的，
> 都应当在**枚举之后**再动手。`SOF_DIAG` / `CAN_DIAG` / `TIME_SYNC` 恰好都只挂在已经初始化
> 好的外设上，所以没踩到；`PULSE_TEST` 是第一个自己开外设的，就踩了。

**上板第一件事仍然是看那一个数，但判据变了**：`measured_ticks_per_microframe_q16()`
应当读出约 **196624000（3000.245）**，而**不是**原文写的 196608000（3000<<16）——理由见本节
开头的更正。判据是：

- 两块板都应落在 **+80 ppm 附近**，且与 2.2 节机器定时器测到的 +81.9 / +80.0 ppm 一致；
- 恰好读出 3000.0000 反而说明**拟合根本没跑**（那正是旧代码的常数）；
- 两块板之间差几 ppm 是正常的（晶振个体差异），差几十 ppm 就要查。

> **UART0 在这个 build 下不工作**（引脚被借走），所以它是独立的编译开关、默认 OFF。

### 5.7 混合速率：一块 HS 一块 FS 能不能共用这条轴 [实测 2026-08-20]

**结论：能，但要改一处策略、补一个 2.8 us 的固定偏置；补完之后跨板 sigma 约 25~30 ns，
只比全 HS 的 20 ns 差一点。**

复现：`-Dlibhcs_USB_FULL_SPEED=ON` 把一块板强制成全速枚举（该开关默认 OFF，是测试载具）。
注意 `tusb_rhport_init` 的 `.speed` 字段**是无效的**——ChipIdea 的 device 驱动只读
`PORTSC1_PORT_SPEED` 汇报，从不强制；真正强制全速的是控制器位 **`PORTSC1.PFSC`**（禁掉
高速 chirp），而且必须在 `tusb_rhport_init` 之后设，因为 `dcd_init` 会复位控制器。

#### 5.7.1 FS 下 FRINDEX 的行为：步长 8，不是 1

| | HS 板（port 1） | FS 板（port 2） |
|---|---|---|
| delta 分布 | **1** @ 100.00000%（159187 次） | **8** @ 100.00000%（19898 次） |
| ISR 间隔均值 | 125.0099 us | **1000.0784 us**（正好 8 倍） |
| FRINDEX 低 3 位 | 0~7 走满 | 恒为 0 |
| 跨板残差 | — | min -12 / p50 -8 / max -3，**不漂移** |

**FRINDEX 永远按微帧计数**，只是全速端口每 1 ms 才收到一个 SOF，所以一次跳 8。残差不漂移
说明两块板数的仍是同一个时钟。

**但现行策略把它判死**：`delta >= 8 -> 计数器不可信 -> invalidate()`。实测后果是 FS 板
`state invalid`、119 次上报 0 次有效、运行期异常 7258、拟合完全没有。修法是按端口速度分档
（`timebase::microframes_per_sof()`，读 `PORTSC1.PSPD`）。改完后两块板都 valid、异常 0、
各自拟合出 +78.9 / +78.6 ppm。

#### 5.7.2 FS 板整条轴晚 2.8 us，原因是 SOF 包自己的传输时间

改完策略后用第 5.5 节的脉冲交换**直接测**（不是推导），三轮：

| | skew 均值 | skew sigma | 通路延迟 |
|---|---|---|---|
| 补偿前 | **-2854 / -2764 / -2810 ns** | 116 / 24.6 / 54.2 ns | 130.4 / 130.8 / 128.8 ns |
| **补偿后** | **+38.6 / +33.7 / +35.0 ns** | 50.1 / **23.9 / 29.9** ns | 130.5 / 130.3 / 128.9 ns |

那 2.8 us 不是玄学，是可以算出来的：

| | SOF 包 | 位时间 | 传输耗时 |
|---|---|---|---|
| FS 12 Mbit | SYNC 8 + PID 8 + 帧号 11 + CRC5 5 + EOP 3 = 35 bit | 83.3 ns | **2.92 us** |
| HS 480 Mbit | SYNC 32 + PID 8 + 11 + 5 + EOP 8 = 64 bit | 2.08 ns | **0.13 us** |
| 差 | | | **2.78 us** |

实测 2.81 us，**吻合到 1%**。机制：**设备是在收完 SOF 包之后才置 SRI 的**，所以在那个中断里
取的任何时间戳都晚了一个包的传输时间。全 HS 的机架上这一项两块板相同、自动抵消，所以以前从未
露头；一旦有一块是 FS，它就变成 2.8 us 的固定偏置。

修法是让每块板减掉**自己那一份**（`timebase::sof_packet_delay_ns()`），于是所有板都对齐到
"包开始"那一刻，与速度无关。补偿后残留 +35 ns、稳定，sigma 25~30 ns。

> **通路延迟在补偿前后、以及 HS/HS 与 HS/FS 之间都是 129~131 ns**，这是尺子没被改坏的旁证：
> 被改动的只有"轴的相位"，物理链路没有变。

#### 5.7.3 代价与建议

能同步不等于该这么用。FS 侧还要付：bulk 端点 64 字节（HS 是 512）、包率低一个数量级、
`sigma` 从 20 ns 退到 25~30 ns、拟合残差从 17 ns 退到 24 ns（SOF 采样率只有 1/8）。
**除非某块板硬件上只能跑全速，否则没有理由混速**；但如果确实混了，这条轴仍然可用。

### 5.6 还没测到的：动作层

以上全部是"板子知不知道现在是第几微帧"，**不是**"板子能不能在第 k 微帧真的动"。后者要等动作层
做出来，而且需要能同时看到两块板的手段：

| 手段 | 分辨率 | 需要什么 |
|---|---|---|
| **GPTMR 脉冲交换**（5.5 节） | 单次 41.7 ns，均值到 ns | **已有接线**，已上板跑通（5.5 节结果） |
| 示波器打两个引脚 | 几十 ns，地面真值 | 一台示波器；单通道也够（见下） |
| 主机侧比对上报 | 一个微帧（125 µs） | 已有，但分辨率不够 |

**单通道示波器够用**：两块板的地已经通过 USB 共用，所以**不能把地夹夹到某块板的 GPIO 上**
（那是把输出脚直接短到地，会烧脚）。正确做法是**两个电阻做电平叠加**：

```
A 的输出 ──[ 1k ]──┬── 探头
B 的输出 ──[ 2k ]──┘
地夹 → 任一块板的 GND
```

节点电压 = (2·V_A + V_B)/3，四个电平可分辨。两块板在同一微帧翻脚时会看到一个**台阶**：台阶在
2.2 V 说明 A 先动，在 1.1 V 说明 B 先动，**电平给符号、宽度给大小**，单通道一次到位。电阻别取
大——10k/20k 的时间常数约 100 ns 会把 130 ns 的台阶糊掉，1k/2k 是 7 ns。用 10x 探头。

## 6. 对齐到本机 Unix 时间

**能，微秒级——但要分清对齐到"本机的 Unix 时钟"和对齐到"真正的 UTC"。**

换算**全部在主机侧**完成（`libhcs::host::time::Timeline`），板子永远不知道 Unix 时间。
这是刻意的：任何 NTP 跳变都不许渗进板端状态机。

- 主机用各板上报的 `(绝对微帧, 往返中点)` 做最小二乘，得到"微帧 -> 本机 steady_clock"；
- 再叠加一个**只在启动时采样一次**的 steady -> system 偏移。持续跟踪会把 NTP 的阶跃
  和调速直接搬进时间轴，包括已经用来排过程的那些微帧。

实测：主机 steady_clock 与 USB SOF 时钟的差异只有 **-0.25 ppm**（拟合出的微帧周期
124999.969 ns），微帧 -> Unix -> 微帧往返误差 **0**。

| 对齐目标 | 可达精度 | 限制来自 |
|---|---|---|
| 本机 Unix 时钟（启动时那一刻的定义） | **微秒级** | 拟合残差 + USB 上下行不对称 |
| 真正的 UTC | 一般**毫秒级** | 本机 NTP 的纪律，本方案无能为力 |
| 板与板之间 | 见第 2 节，与主机时钟**无关** | 硬件微帧计数器 |

要微秒级 UTC 得上 PTP 或 PPS，这里做多少工作都换不来。

## 7. 还没做的事

### 7.1 直接实测跨板 σ（已完成 2026-08-20）

第六条路（5.5 节 GPTMR 脉冲交换）**已经跑通并给出数**：跨板 skew 1 sigma 约 20 ns、
通路延迟 129 ns，见 5.5 节的结果表。两侧代码齐备（`Handler::send_pulse_schedule` 的定义、
板级转发、协议的 `Flags` 回执、主机工具 `host/examples/pulse_skew_test.cpp`）。

上板当天修掉的三个缺陷都值得记住，因为**每一个都会让测量静默失败而不是报错**：
时钟门控漏加（变砖）、比较器极性反了（捕到的是脉冲后沿，均值恰好等于脉宽）、
微帧编号向后跳时采样器永久卡死（400 轮全部拒绝武装，看起来像断线）。

复现顺序（工具自己就是按这个顺序打印的，不要跳）：

```bash
export GNURISCV_TOOLCHAIN_PATH=~/3rd_party/rv32imac_zicsr_zifencei_multilib_b_ext-linux
export PATH="$GNURISCV_TOOLCHAIN_PATH/bin:$PATH"

# 0. 先证明那根 UART0 线是通的，再把它借走当定时链路
./host/build/examples/dual_board_test link          # 只看两行 UART0，必须双向 PASS

cmake --preset release -S firmware/hpm_board -B firmware/hpm_board/build_5321_pulse \
      -DBOARD=hpm5321 -Dlibhcs_TIME_SYNC=ON -Dlibhcs_PULSE_TEST=ON
cmake --build firmware/hpm_board/build_5321_pulse --target hpm_board_app
IMG=firmware/hpm_board/build_5321_pulse/app/output/hpm_board_app_hpm5321.dfu
dfu-util -p 3-1 -a 0 -D $IMG && dfu-util -p 3-2 -a 0 -D $IMG

cmake --build host/build --target pulse_skew_test
./host/build/examples/pulse_skew_test 400 400       # 400 轮，提前量 400 微帧 = 50 ms
```

1. **第 1 段：两块板拟合出的 tick/微帧**。应当是约 **3000.245（+80 ppm）**，与 2.2/4.4 节
   的晶振偏差对得上；**读出恰好 3000.0000 说明拟合没跑**。不对就停，别往下看。
2. **第 2 段：单向偏移的离散度**——这就是这把尺子的噪声底。1 tick = 41.7 ns，量化底约
   12 ns（41.7/sqrt(12)）；明显大于它就是真抖动，先查抖动再谈 skew。
3. **第 3 段：双向和 / 双向差**。和的一半是通路延迟（电缆 + pad + 施密特，常数，不是
   skew）；差的一半才是跨板 skew。

**任何时候第 2 段不干净，第 3 段一眼都别看**——第 5.4 节五次失败全是违反这条的代价。

> 工具会先跑 24 轮**丢弃**的热身：板子在收到第一条 schedule 时才把 GPTMR 拉起来
> （5.5 节的"教训"一段说明了为什么），拟合还要一秒钟才收敛。

### 7.2 动作层

时间轴能用了，缺的是**用它做事**：目前 `timebase::local_time_of()` 已能把任意微帧换成本地定时器
刻度，但**没有任何下行字段带执行时刻，板端也没有到期调度器**。这块板是 CAN/UART 桥，唯一能调度
的动作是"在第 k 微帧发这一帧 CAN"。

**正确做法不是在中断里发**，而是：主机提前 3~5 ms 下发"帧 + 执行微帧"，板子**收到就立刻**
反序列化并 `mcan_write_txbuf()` 预置进专用 TX buffer 但**不请求发送**；到点只做一件事
`mcan_send_add_request()`，展开就是 `TXBAR = 1<<index`，**一条寄存器写**。于是序列化时间只决定
**提前量要留多少**，永远不决定**抖动**。

提前量起点 3~5 ms，**必须实测传输延迟 99.9 分位再定**；本机连主机调优都没做（见 4.5），现在测
没有意义。还要做过期指令丢弃与计数。

更好的路是 4.7 节的 `PTPC_CMP0` → TRGM：**到点硬件触发，CPU 完全不参与**，这才是 SYNC0 的等价物。

### 7.3 其他缺口

- **更多板子与 hub 拓扑**：目前只验证了两块板、根口直连。
- **长时间与温度**：最长 60 秒，室温。
- **失效与恢复行为的量化**：状态机写了，异常分支在本机是死代码（delta 2~7 从未触发）。
  **不要因为没触发就删掉**——换主机控制器或加板子都可能让它复活。
- **PTPC 驯服路线**（4.7 节）：如果要走"CAN 时间戳直接落在共享轴上"，这条比 GPTMR 脉冲更根本。
